# Rubric: test case designer

## Choosing a technique

| The criterion has | Use | Why |
|---|---|---|
| a limit (`at least`, `up to`, `from X to Y inclusive`, `below`, `above`) | boundary, plus partition | defects cluster at the edges; the classes either side have different outcomes |
| a list of allowed values or outcome classes | partition | one representative per class, invalid classes included |
| conditions that combine (`when`, `if`, `unless`, `but never`) | decision table | every combination is a rule; missing rules are where the defects hide |
| statuses and changes (`becomes`, `when it is`, `can't be`) | state transition | every valid transition, and every event that must be refused |
| three or more independent parameters (`every payment method, every delivery option`) | pairwise | all pairs in a fraction of the combinations |
| a flow | scenario | the main flow and each alternative |
| none of these, but known failure modes | error guessing (agent judgment) | lower confidence; say why each case was chosen |

Several techniques can apply to one criterion; the model lists each with its reason.

## Rows

| Technique | Rows generated by `design_rows.py` |
|---|---|
| boundary | for each limit: `value - step`, `value`, `value + step` |
| partition | one per class |
| decision table | the full product of the conditions' values |
| pairwise | a greedy all-pairs covering (strength 2), honouring constraints; small spaces search every combination for each row |
| state transition | each valid transition; each (state, event) not in the transitions |
| scenario | one per flow |

Every row is covered by a case or listed under `infeasible` with a reason. A case may cover several rows
of its criterion and technique (for example every refused event in one state).

## Expected results

Observable only: a number, a message, a status, an element on the page. Rejected phrases are in
`data/expected-terms.json` (works, correct, as expected, properly, successfully, promptly, immediately,
...). A timing needs a number and a unit.

## Priority

| Rule | Effect |
|---|---|
| Base | the ticket's priority: Highest P0, High P1, Medium P2, Low P3 |
| `boundary` or `negative` case on a `money` criterion | one level up |
| cosmetic check (`cosmetic: true`) | one level down |

## Test data

Emails at reserved domains (`example.test`, `example.com`, `.test`, `.invalid`); card numbers only from
the published test numbers in `data/expected-terms.json` (a number that passes the Luhn check and isn't one
is rejected); invented names.

## Questions

A vague term in a criterion (shared ambiguity lexicon, or a timing word without a number) is a question
unless dismissed with a reason. Questions the agent raises itself are `agent_judgment`. A case whose
expected result relies on an answer lists the question; the question lists the cases it blocks.
